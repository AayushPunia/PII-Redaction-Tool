# PII Redaction Tool for SEBI Red Herring Prospectus

A production-quality tool that detects and redacts Personally Identifiable
Information (PII) from a real SEBI Red Herring Prospectus (`.docx`), replacing
each PII value with a realistic, consistently-mapped fake value generated by
Faker.

---

## Quick Start

```bash
# 1. Install dependencies
pip install -r requirements.txt
python -m spacy download en_core_web_sm

# 2. Place the input file
mkdir -p input
cp /path/to/Red_Herring_Prospectus.docx input/

# 3. Run
python redact.py

# 4. Output
ls output/redacted_output.docx   # ← the redacted document
```

## Approach

### Architecture: Hybrid Regex + NER under Presidio

The tool uses a single, unified [Microsoft Presidio](https://github.com/microsoft/presidio)
pipeline — not two separate ad hoc passes. This design was chosen because:

1. **Structured PII** (emails, phones, CINs, PANs, DINs, credit cards) is
   best caught by validated regex patterns — NER alone would miss them or
   hallucinate boundaries.
2. **Contextual PII** (person names, company names, physical addresses) is
   best caught by NER (spaCy's `en_core_web_sm` model) — regex alone can't
   reliably parse natural-language name/address mentions.
3. Registering all detectors as Presidio `PatternRecognizer` /
   `EntityRecognizer` subclasses means **adding a new PII type** is a
   single-file addition (`recognizers/new_type.py`) plus one `registry.add()`
   call — no structural changes needed.

### NER Model Choice: `en_core_web_sm`

We use spaCy's `en_core_web_sm` (12 MB) rather than `en_core_web_lg` (560 MB).
Given the time constraint and the fact that our custom regex recognizers
already cover the highest-value structured entity types (emails, phones, CINs,
DINs, PANs), the NER model's primary job is person-name and company-name
detection where the smaller model is adequate. The trade-off:

- **`en_core_web_sm`**: Faster, smaller, may miss some uncommon names or
  misclassify some entities in dense legal prose.
- **`en_core_web_lg`**: Better accuracy on formal/legal text, especially for
  less common names and multi-word location phrases, at the cost of 50×
  larger download.

If upgrading, change the single `model_name` variable in `build_analyzer()`.

### Three-Pass .docx Processing

The tool makes three distinct passes over the Word document:

1. **Run-based pass**: Iterates every paragraph's runs — top-level
   paragraphs, all 76 tables (rows → cells → paragraphs → runs), and all
   headers/footers. Reconstructs full paragraph text from runs to detect PII
   spans that cross run boundaries (Word often splits a single word across
   multiple `<w:r>` elements due to spell-check or revision history), then
   maps character offsets back to individual runs for replacement.
   Also processes runs inside `<w:hyperlink>` XML elements, which python-docx's
   `paragraph.runs` property silently skips.

2. **Field-code pass**: Finds and redacts `<w:instrText>` field-code content —
   specifically `HYPERLINK "mailto:..."` instructions — via direct XPath on
   the document's XML. These are a hidden PII surface separate from the
   visible display text: in this document, the visible text
   `kshinternational.ipo@in.mpms.mufg.com` has a hidden field-code target of
   `ksh@in.mpms.mufg.com` — a different real email that Pass 1 cannot see.
   Both are redacted, consistently.

3. **Relationship-parts pass**: Iterates `document.part.rels` for external
   hyperlink relationships (`TargetMode="External"`). For this specific
   document, direct inspection of `document.xml.rels` confirms **zero**
   r:id-based external hyperlink relationships exist — only font/header/
   footer/image/style relationships. The pass verifies this at runtime and
   reports the count (expected: 0) rather than skipping it.

> **Finding**: Checked two separate Word hyperlink storage mechanisms (inline
> field codes and relationship parts). Found and fixed a real PII leak in the
> first mechanism; verified the second was empty in this document but
> implemented the check for completeness.

### Fake Replacement with Consistent Mapping

- Uses `Faker('en_IN')` so substitutions (names, addresses, company names,
  phone numbers) read as native to an Indian legal document.
- Maintains a single `dict[(entity_type, normalized_text)] → fake_value`
  mapping. The same original PII value always maps to the same fake value,
  everywhere in the document.
- **Name-variant coalescing**: Honorifics (`Mr.`/`Mrs.`/`Ms.`/`Dr.`/`Shri`/
  `Smt.`) are stripped before lookup and preserved in output. Single-word
  name mentions (e.g., "Sarthak") are resolved to a previously mapped full
  name (e.g., "Sarthak Malvadkar") **only if that full name appears in the
  same paragraph or table cell** (local anaphora resolution) — not by global
  substring matching, which would silently merge two different people who
  share a first name into one fake identity.

### Custom Recognizers

| Recognizer | Entity Type | Pattern / Strategy | Base Score | Context Boost |
|---|---|---|---|---|
| `CINRecognizer` | `IN_CIN` | `[UL]\d{5}[A-Z]{2}\d{4}(PLC\|PTC\|...)\d{6}` | 0.85 | CIN, Corporate Identity |
| `PANRecognizer` | `IN_PAN` | `[A-Z]{5}\d{4}[A-Z]` | 0.50 | PAN, Permanent Account |
| `DINRecognizer` | `IN_DIN` | `\b\d{8}\b` | 0.30 | DIN, Director, Designation |
| `GSTINRecognizer` | `IN_GSTIN` | `\d{2}[A-Z]{5}\d{4}[A-Z]\d[A-Z\d][A-Z\d]` | 0.90 | GSTIN, GST |
| `IndiaPhoneRecognizer` | `PHONE_NUMBER` | `+91...`, `0XX-...`, 10-digit mobile | 0.40–0.75 | Telephone, Contact |
| `CreditCardLuhnRecognizer` | `CREDIT_CARD` | 13–19 digits + **Luhn checksum** | 0.80 | — |
| `DOBRecognizer` | `DATE_OF_BIRTH` | Date patterns near "born"/"DOB"/"age" | 0.75 | — |
| `SpacyOrgRecognizer` | `ORGANIZATION` | spaCy NER `ORG` label | 0.60 | — |

**GSTIN vs. PAN overlap**: GSTIN embeds a full PAN as a substring (chars 3–12).
GSTINRecognizer's score (0.90) is deliberately higher than PANRecognizer's
(0.50) so Presidio's overlap resolution picks the longer, more specific GSTIN
match when both fire on the same span.

**Credit card Luhn validation**: The Luhn checksum is the single biggest
precision improvement — without it, CINs, phone fragments, and reference
numbers would false-positive as credit cards. **Known residual limitation**: 
~10% of random digit strings pass Luhn by chance, so a real bank account
number could occasionally be misclassified. This is accepted as a residual
risk rather than hidden.

## Explicit Judgment Calls

These are deliberate policy decisions, not oversights.

### 1. Subject Company Name Is Not Redacted

"KSH International Limited" (and its abbreviation "KSH") is the subject of
the entire prospectus. Redacting it would make the document nonsensical —
every sentence refers to "our Company" or "KSH" in context. The tool
maintains an exclusion list matching the subject company's name variants and
skips them during replacement. Other company names (banks, law firms,
registrars, group companies) **are** redacted because they are identifiers of
distinct third-party entities.

### 2. CIN / PAN / DIN / GSTIN Are Treated as PII

These are regulator-issued identifiers that are uniquely tied to specific
individuals (DIN, PAN) or entities (CIN, GSTIN). Their presence in a document
enables re-identification of the person or entity even if their name is
redacted. Treating them as PII and replacing them with structurally valid
fakes is the conservative, privacy-preserving choice. The alternative
(leaving them because they're "public record") would undermine the purpose of
the redaction exercise.

### 3. Page Numbers, Section References, and Financial Figures Are Left Alone

These are structural/factual data, not personal identifiers:
- **Page numbers / section references** (e.g., "see page 250") are document
  navigation aids.
- **Financial figures** (e.g., "₹4,200.00 million") are the substance of the
  filing — redacting them would destroy the document's analytical value with
  zero privacy benefit.
- **Dates** that are filing dates, fiscal year boundaries, or regulatory
  deadlines are NOT dates of birth and are not redacted.

### 4. Precision / Recall Trade-off

This is a data-pipeline context — the hiring company builds training data
pipelines for AI. In this setting, **both** under-redaction (privacy leak) and
over-redaction (data quality destruction) are harmful:

- **Under-redaction** leaks real PII into downstream datasets, creating
  compliance risk.
- **Over-redaction** destroys the factual content that makes the document
  useful as training data — replacing financial figures, section references,
  or generic terms with fakes renders the text incoherent.

We therefore **target balanced precision and recall (optimizing F1)** rather
than asserting "recall always wins." Concretely:
- Context-dependent recognizers (DIN, DOB) use low base scores that only
  cross the detection threshold when contextual cues confirm the type,
  sacrificing some recall for significant precision gains.
- The Luhn checksum for credit cards rejects ~90% of false-positive
  candidates.
- The subject-company exclusion preserves the most-referenced entity in
  the document.

### 5. Full Image Replacement over Selective OCR Masking

The document contains two embedded ID card images (a PAN card and an Aadhaar card)
containing real, sensitive, high-value PII not reachable via text analysis.
Instead of attempting field-level OCR masking (blurring just the DOB or ID number), 
which poses a real reliability risk under time constraints, the tool performs **full image replacement**.
It targets these two specific identified images (via their `target_ref` in `.rels`) 
and replaces their binary content with a solid-color placeholder matching the original pixel dimensions. 

This guarantees zero PII leakage while preserving the document's structure, anchors, and positioning.
A production system would ideally use OCR-based field-level redaction instead of full replacement. 
Note: this approach explicitly targets these two known images and does not generically detect 
ID-card-like images elsewhere in the document.

## Known Limitations

1. **Full multi-line addresses**: NER detects location components (city names,
   states, pin codes) individually but may not capture a complete street
   address as a single span. A purpose-built address parser would improve
   this.
2. **Name detection in tabular context**: spaCy's NER occasionally misses
   names that appear as bare entries in table cells without surrounding prose.
3. **DIN false negatives**: The very low base score (0.3) means a DIN will be
   missed if no context word ("DIN", "Director", "Designation") appears nearby
   in the same paragraph text — a deliberate precision-over-recall choice for
   8-digit numbers.
4. **Luhn residual**: ~1 in 10 random digit strings pass Luhn, so a bank
   account number could theoretically be flagged as a credit card.

## Extending to a New PII Type

1. Create `recognizers/new_type_recognizer.py` — subclass `PatternRecognizer`
   (for regex) or `EntityRecognizer` (for custom logic).
2. Add the import to `recognizers/__init__.py`.
3. In `redact.py`, add `analyzer.registry.add_recognizer(NewTypeRecognizer())`
   in `build_analyzer()`.
4. Add the entity type string to `SUPPORTED_ENTITIES`.
5. Add a Faker generator in `EntityMapper._generate()`.

No structural changes to the pipeline, validation, or .docx handling code.
